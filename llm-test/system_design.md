## Step 2.1: Estimate Token Usage (5 pts)

To estimate the overall computational requirements and operating costs for SafeSpace, we will have to first estimate the number of tokens used and processed during an AI request. Input tokens represent the text sent to an AI model, and the output tokens represent the text generated by the AI model.

In our previous assignment, P1-A6 Production Reflection, we used a scenario of 10,000 active daily users to explore SafeSpace’s potential AI costs. We assumed that each user would make an average of 3 AI requests per day, which comes to an average of 300 input tokens and 100 output tokens per request. These figures are planning assumptions rather than taking measurements from 10,000 actual users; the estimates serve as the starting point for our cost analysis in this assignment.

Based on these assumptions, each request would be using approximately 400 tokens in total. With 3 AI requests per user per day, the estimated daily consumption is 900 input tokens and 300 output tokens per user, totalling 1200 tokens combined.

Because these aren’t real measures of actual production usage, the amount could vary once in production. Our previous implementation used separate local and external AI components, and the token consumption varied depending on the task and prompt length. For example, the local-quest generation prompt uses a longer prompt beyond the quest recommendation, which contains the existing quest list, examples, and additional context. In our previous assignment, this prompt was estimated to use approximately 800 input tokens per request. This is a task-specific estimate and does not mean that every AI request will use 800 input tokens. The external AI component that generates a personalized welcome message also has different input requirements. However, for consistency sake, this analysis will be using the 300-input-token and 100-output-token assumption as a baseline, while recognizing that the actual usage and costs may differ in the long-run. The approximately 800-input-token estimate will be considered later when discussing the limitations of the baseline and the potential differences in actual operating costs.

## Step 2.2: Compute Total Token Load (5 pts)

To estimate SafeSpace’s AI workload among different levels of growth, we calculated the number of tokens processed every day across the 6 Daily Active User (DAU) categories as shown in the assignment. Based on Section 2.1, we assume that each user makes around 3 AI requests per day, with an average of 300 input tokens and 100 output tokens per request. This results in an estimated 1,200 tokens per user per day. The daily input and output token load is calculated using the following formulas:

```
Daily Input Tokens = Daily Active Users × 900
Daily Output Tokens = Daily Active Users × 300
Total Daily Token Load = Daily Active Users × 1,200 tokens
```

For example, at the Prototype level, 1,000 daily active users would generate approximately 1,200,000 tokens per day. At the Global Platform level, 100,000,000 daily active users would generate approximately 120,000,000,000 tokens per day.

| Daily Traffic Category | Daily Active Users | Daily Input Tokens | Daily Output Tokens | Total Daily Tokens |
|---|---|---|---|---|
| Prototype | 1,000 | 900,000 | 300,000 | 1,200,000 |
| Early Startup | 10,000 | 9,000,000 | 3,000,000 | 12,000,000 |
| Growing Product | 100,000 | 90,000,000 | 30,000,000 | 120,000,000 |
| Large Platform | 1,000,000 | 900,000,000 | 300,000,000 | 1,200,000,000 |
| Mass Consumer App | 10,000,000 | 9,000,000,000 | 3,000,000,000 | 12,000,000,000 |
| Global Platform | 100,000,000 | 90,000,000,000 | 30,000,000,000 | 120,000,000,000 |

\* figures are based on token-usage assumptions shown in 2.1 (not actual production traffic)

These results show that SafeSpace’s daily AI workload increases proportionately with its number of active users. However, actual token consumption may vary by AI task. For example, the local quest-generation prompt may require approximately 800 input tokens rather than the 300-token baseline. If these longer prompts were to make up a significant portion of daily requests, the actual input token consumption could be much higher.As the exact frequency of each AI task has not been established, the current 300 baseline assumption will be used across all 6 traffic levels to maintain a consistent comparison. These estimates will be referenced in the following sections to compare local hosting costs with Hugging Face Inference API costs at each traffic level.

This configuration is a reasonable starting point because it matches the example hardware specifications in the assignment: a 16-core CPU, GPU-enabled computing, and 64 GB of RAM. The estimated monthly cost represents the cost of running one Google Cloud g2-standard-16 machine continuously for 30 days. It does not establish how many daily active users that one machine can support.

### Estimating daily token capacity per machine

To estimate the number of machines required, we first estimate how many tokens a single machine could process over the course of a day. This calculation uses the inference throughput for each model and a 20% utilization factor.

### Rationale

The effective throughput values in the spreadsheet are preliminary planning estimates based on model size and expected computational requirements. Because smaller models generally require less computation per generated token, they were assigned higher initial throughput estimates. Larger models were assigned lower estimates to reflect their potentially greater computational demands.

The estimates are grouped into the following ranges:

- Tiny models: ~100–120 tokens per second.
- Ultra-light models: ~65 tokens per second.
- Small models: ~40–45 tokens per second.
- Medium models: ~25 tokens per second.
- Larger models: ~12–20 tokens per second.

These ranges provide a consistent starting point for comparing the 15 models under the same planning approach. However, model size alone does not determine throughput. Actual performance also depends on the GPU, model precision, inference software, batching, prompt length, and workload. Therefore, these values are assumptions for estimating infrastructure requirements and not verified performance values for every model on the selected Google Cloud L4 machine.

Our previous model evaluation provided response-time measurements on a Colab T4 GPU. Those measurements helped us compare model response latency, but they also do not validate the throughput assumptions for the Google Cloud L4 configuration. The throughput estimates should be treated as preliminary until tested under the intended configuration.

### Capacity Utilization Assumption

The calculation also applies a 20% capacity utilization factor. The 20% utilization factor is a planning assumption intended to avoid treating the estimated throughput as fully sustained capacity throughout the day. The 20% factor has not been validated through production load testing and is not a measured property of the selected machine.There are 86,400 seconds in one day (24 * 60 * 60). We calculate estimated daily token capacity per machine using the following formula:

```
Estimated Daily Token Capacity = Throughput (tokens/second) × 86,400 × 20%
```

For example, if the throughput used for a model is 100 tokens per second, the estimated daily token capacity would be:

```
100 × 86,400 × 0.20 = 1,728,000 tokens per machine per day
```

This example illustrates the calculation, but it does not fully establish that every model achieves 100 tokens per second. The throughput should be identified as an assumption; if a throughput has been adjusted for 20% utilization, the utilization factor is applied once in the daily capacity formula.

### Estimating the number of machines needed

After the total daily token load and estimated daily capacity per machine is calculated, we estimate the number of machines required by dividing the workload by the capacity of one machine and rounding it up to the nearest whole machine.

```
Machines Needed = Total Daily Token Load ÷ Estimated Daily Token Capacity per Machine (round up)
```

For example, if the daily token load is 1,200,000 tokens and one machine’s estimated capacity is 1,728,000 tokens, the calculations above would give one machine. If the workload exceeds a machine’s estimated capacity, the result is rounded up to determine a fair number of machines needed.

These calculations explain the relationship between the spreadsheet columns. Total daily token load represents the estimated workload, daily token capacity per machine estimates the workload a single machine can handle, and machines needed estimates how many machines are required to handle the workload.

## Step 2.4: Hugging Face Inference API Cost Comparison (30 pts)

To compare local hosting with a hosted API, we used the same 6 traffic categories as Section 2.3. For the API estimate, we chose the Qwen/Qwen3-4B-Instruct-2507 through Nscale via Hugging Face Inference Providers as a pricing baseline. This is not the same model as our local Qwen/Qwen2.5-0.5B-Instruct model, and its price should not be taken as the confirmed price across all 15 models.

Pricing source: <https://huggingface.co/inference/models?search=Qwen3-4B-Instruct-2507>

The listed Nscale rates are:

- Input tokens: \$0.01 per 1 million tokens
- Output tokens: \$0.03 per 1 million tokens

These rates were checked against the Hugging Face Inference Providers model listing and should be re-verified before deploying, because the provider pricing can change.

Assumptions:

- Each user makes an average of 3 AI requests per day
- Each request uses an estimated 300 input tokens & 100 output tokens
- Daily input tokens per user: 3 x 300 = 900
- Daily output tokens per user: 3 x 100 = 300
- Daily tokens per user: 900 + 300 = 1,200
- Assume 30 day month
- Calculation uses the listed Nscale rates for Qwen/Qwen3-4B-Instruct-2507 through Hugging Face Inference Providers: \$0.01 per million input tokens and \$0.03 per million output tokens.
- API machine counts are marked N/A b/c the provider manages the serving infrastructure.

### Cost Calculation

```
Daily Input Tokens = DAU × 900
Daily Output Tokens = DAU × 300
Daily API Cost = (Daily Input Tokens ÷ 1,000,000 × $0.01) + (Daily Output Tokens ÷ 1,000,000 × $0.03)
Estimated 30-Day API Cost = Daily API Cost × 30
```

For example, at 1,000 DAU:

- Daily input tokens = 1,000 × 900 = 900,000
- Daily output tokens = 1,000 × 300 = 300,000
- Daily API cost = (900,000 ÷ 1,000,000 × \$0.01) + (300,000 ÷ 1,000,000 × \$0.03) = \$0.018
- 30-day API cost = \$0.018 × 30 = \$0.54

# Part 3: Multi-Model Routing Strategy (50 pts)

## 3.1: Define Five System Scenarios

| Scenario | Description |
| :--- | :--- |
| **Quest Fulfillments** | Standard traffic of daily quest completion. |
| **Evening Rush** | Spike of traffic later in the day due to journal logging and rewards being unlocked. |
| **Journal Breakdowns** | Turning long or emotional journal entries into personalized quests and helpful feedback. |
| **Offline Time** | When a user has weak service or no internet connection. |
| **Server Overload** | Sudden traffic spikes or server crashes that slow down or stop the cloud service. |

---

## 3.2: Design Routing Strategies

| Scenario | Routing Strategy | Local Model Used | Hugging Face Model Used | Expected Benefit |
| :--- | :--- | :--- | :--- | :--- |
| **Quest Fulfillments** | Use tiny local models for quick actions and small cloud models for simple requests. | `Qwen/Qwen2-0.5B-Instruct` | `Qwen/Qwen2.5-1.5B-Instruct` | Super fast response times and low server bills. |
| **Evening Rush** | Move simple text generation to the device so the servers don’t slow down during busy hours. | `unsloth/Llama-3.2-1B-Instruct` | `tiiuae/Falcon3-3B-Instruct` | Stops app from lagging or crashing when many people log in at once. |
| **Journal Breakdowns** | Send personal, detailed journal entries only to smart cloud models that can handle deep thoughts. | *(None — saved for storage space)* | `microsoft/Phi-4-mini-instruct` <br>**OR**<br> `unsloth/Llama-3.2-3B-Instruct` | Gives high-quality, caring, and safe feedback for personal journal entries. |
| **Offline Time** | Run basic features directly on the device without needing any internet connection. | `Qwen/Qwen2.5-0.5B-Instruct` | *(Not capable — no internet connection)* | Keeps the app working anywhere, even without Wi-Fi or data. |
| **Server Overload** | Stop calling the cloud and let device handle basic app tasks until servers fix themselves. | `unsloth/Llama-3.2-1B-Instruct` | *(Temporarily disabled during cloud crash)* | Keeps the app running safely instead of shutting down or showing error screens. |

---

## Step 3.3: Evaluate the Strategy
The strategy reduces latency by using fallback options in cases where a cloud service is unavailable or when demand is too high for it to handle. More capable cloud models would handle requests when demand is medium or low, offloading work to local models when demand is too high. This reduces strain on cloud models, which reduces latency during peak hours. Secondly, simple and low-priority tasks are handled by local models instead of the cloud service, which further reduces traffic.

The strategy reduces cost by minimizing dependency on paid services. The same strategies that offload work to local models also saves money by not requiring a paid API to handle all of the work. This means that the cost per user is heavily reduced, and users that don't use features that require cloud models are effectively free.

The strategy preserves output quality by assigning models based on task priority and simplicity. Local models are assigned to simple tasks where error are already unlikely, and any mistakes would be simple and unimportant. Larger tasks that handle more information or are more important are assigned to larger models built for them, which keeps quality high. In either case, the model chosen is likely to handle the task with little issue. The fallback options also prevent errors by ensuring that tasks are still handled by a temporary model until the API is available again.
